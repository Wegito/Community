# Decisions log

Deviations from [`ROADMAP.md`](ROADMAP.md) and other decisions worth remembering. Newest first.

## 2026-10-12 — M1 review fixes

64. **Nobody gets a usable invitation for rights they lack.** Before inviting, `members.email_only_reason()` compares the permissions a login for the member would carry (rank, Ämter, groups, direct roles; today and on every later day one of them starts) with what the inviter holds or may give a new member as starting rank (decision 37). If the member's go beyond that, there is no link or QR code and the inviter cannot choose the address: only an email to the member's stored contact email is sent, and without one only someone with these rights can invite. The page "Einladen" says so and offers only that choice. Permissions are compared, not roles, so at go-live the Fuxmajor (a Bursch) still invites plain Burschen, Füchse and Alte Herren by link, while a Senior or Kassenwart without login only gets a mail to their own address; and the technical admin, who has no rank, can still invite new Spefuxe by link. Import invitations go to the address in the file and always pass. Left open: a holder of `members.edit_any` can change the contact email first and then invite; that change is audited with old and new values (decision 27). Refusing addresses the inviter entered was rejected, because in the bootstrap the admin imports exactly those addresses.
65. **The invitation link leaves the session with the login.** The raw token still lives in the signed (not encrypted) session cookie, so the result page survives a reload (decision 35). Every `logout_user()` (Abmelden, Überall abmelden, password reset) removes it at once. A login ended elsewhere ("Überall abmelden" on another device, a locked login) logs nobody out in this browser; there the next request without the inviter's login removes it, before anyone can log in with that cookie. Showing the link only once was rejected: phones often reload the page while the inviter switches to the messenger or shows the QR code. Encrypting the token would need a new dependency.
66. **One rule for ending a period now.** `valid_to` is inclusive (D5). A rank, Amt, group membership or direct role ended "today" kept its rights until midnight, and one that had not started yet shrank to a one-day period: it blocked the successor (`max_holders`, "ist bereits in"), showed the person as holder on that day and came back with a Wiederaufnahme. Now every end has a last day, and a period that starts after its last day never takes effect and is deleted, with an audit entry (`org.office.cancel`, `org.group.cancel`; deleted ranks and direct roles appear in the `members.exit`, `org.rank.change` or `authz.member_role.revoke` entry). Ending *now* makes yesterday the last day: "Entfernen" on a group page, and `flask authz revoke`, which now also catches grants that start later. An Austritt uses the exit date as the last day (this replaces the last sentence of 29), a rank change the day before the new rank. "Beenden" for an Amt keeps its explicit "Letzter Tag". An Amt that starts today or later can instead be "Ausgetragen" (deleted), so an Amt given to the wrong member goes to the right one the same day; likewise a rank that starts today or later is replaced by a new rank from the same day (e.g. the Fuxmajor's Spefux becomes Fux). A period that began before today stays in the history; only a backdated Austritt or rank change deletes one, since it should never have applied. The office and group pages also list periods that start later ("ab …"). Nothing refers to these rows, so deleting them is safe. SQLite may give a new row the id of a deleted one, so the audit entries also name the Amt or group and the member. A cancelled flag was rejected: every query on these tables would have to remember it.
67. **An Amt needs an eligible rank for its whole term.** Unless kommissarisch, `assign_office` checks the rank on the first day and every rank entry recorded for later (e.g. a Philistrierung entered in advance) and refuses with the date of the first rank that may not hold the Amt. Ending the term automatically the day before was rejected: nobody would notice. In the other direction, a rank change now handles every Amt still running on or after its date, also one that starts later (§6.4: end or keep kommissarisch), and "Rang ändern" lists those too.
68. **Rank periods never overlap, and former members get none.** After a Wiederaufnahme the new rank has to start after the last one ended (28); the form suggests that day, so someone who left today and is taken back today has a rank from tomorrow. `change_rank` refuses former members. The rank page follows 23 and 32: a former member's page is a 404 unless one may see former members, and then shows only the history. `can_see_former_members()` moved to `core/authz/policies.py`, which both blueprints use.
69. **`flask setup` runs after every `flask db upgrade`** (first install, update from M0, every later update). It refuses to run before all migrations have run, copies the declared permission codes into the database (`flask authz sync`) and adds default grants from `seed/authz.yaml`: all of them while no role has any grant (new install, update from M0), afterwards only those of codes that are new in the database, e.g. the finance codes when M3 arrives. A grant removed on purpose therefore stays removed (§6.2); `flask setup --seed` or `flask authz seed` adds every missing default grant again. It then says what is missing: an admin (`flask create-admin`) and members without rank. `flask create-admin` warns when the admin role has no grants yet. Rejected: default grants in a data migration (the codes are declared in code, and later modules add theirs), and seeding inside `create-admin` (an update from M0 runs no `create-admin`). The README's install and M0-update steps are run end to end in `tests/test_setup.py`.
70. **"Ohne Rang" gives members who never had a rank their first one** (*Verwaltung → Ohne Rang*, `members.import`). After the update from M0 every account is such a member (§5.11: rank cannot be derived), and so are import rows without rank. The page lists active members without any rank entry; the chosen ranks start on one date, today or earlier, through `change_rank` (audited as `org.rank.change` with `from: null`), without notification, like the import. This extends 53: whoever may import members with any initial rank may also give an existing member without rank their first one, which gives nothing an import with an email invitation would not. Not offered: one's own rank (§6.3 rule 1; the server operator uses `flask org set-rank`, which now also finds members without login by their contact email), members after a Wiederaufnahme (28: "Rang ändern" with `members.rank.change`), and later changes. An Amt held kommissarisch before the first rank stays kommissarisch. Letting the import match existing members by email was rejected: it would turn the error of 52 into a silent update of someone else's row.
71. **Grants added by the seed are audited** (`flask authz seed`, `flask setup`): one `authz.role_permission.grant` entry per role with its new codes, the sensitive ones listed again under `sensitive`, and the seed file's name; the actor is empty for the CLI. The notification of the Senior and the Kassenwart for sensitive grants (§6.3 rule 5) comes with the matrix UI (M7-6), the first place where grants change in the app; at the first install neither office is filled.
72. **The audit log's IP retention runs from `flask jobs tick`.** Each tick queues the job `audit.purge_ips` with the dedupe key `audit.purge_ips:<date>` (decision 14), so it runs once a day, at the first tick after midnight, however often the tick runs; it removes IP addresses older than `AUDIT_IP_RETENTION_DAYS` (default 90, now in the README and `.env.example`). `daily_job()` in `jobs.py` registers such housekeeping. A second cron line for `flask audit purge-ips` was rejected: servers set up from the README would miss it. The period itself is reviewed in M8-7.
73. **`flask create-admin` for a member without login** (imported, or created with "Neues Mitglied") gives that member the login, matched by contact email; the member's name stays as it is. It refuses former members and the contact email of a member who logs in with another address, instead of creating a second member with the same email.

## 2026-10-11 — M1

14. **M1-6: a job's `dedupe_key` stands for work that happens once.** `enqueue()` returns the existing job whatever its status, also when it is done or failed, so a reminder that was sent is never sent again. A failed job runs again only through `flask jobs retry` or the retry button on `/admin/jobs`, which also resets its attempts. Concurrent duplicates are stopped by the unique constraint (the second transaction fails); there is no savepoint retry, because SAVEPOINT handling in pysqlite is unreliable.
15. **M1-6: `attempts` counts runs started, not only failures.** The claim increments it. A tick that dies mid-job leaves the job `running`; the next tick releases it after its 5-minute lock as a failed attempt. Jobs therefore run at least once, and a crash loop still ends in `failed`.
16. **M1-6: mails are rendered when queued.** Each `templates/mail/<name>.txt` extends `mail/base.txt` (greeting, signature, footer with `CLUB_NAME`) and defines `subject` and `body` blocks. The subject is the `subject` block rendered alone; the body is the whole template. The job only sends text, so it needs no request. Links use `BASE_URL` and fall back to the request's host; without either (CLI), `notify()` sends the mail without links.
17. **M1-6: `/admin/jobs` never shows payloads,** only a short summary per job kind (for mails: recipient and subject). Mail bodies will contain password-reset and invitation links, and the technical admin must not be able to take over other accounts such as the Kassenwart's (roadmap §6.3, rule 6).
18. **M1-6: `office_assigned` and `rank_changed` are sent from the org routes, not the services.** Bootstrap through `flask org set-rank` and the test factories stays silent and needs no request or `BASE_URL`.
19. **M1-6: notification pages are part of core** (`community/core/platform/routes.py`, blueprint `notifications`), because every module sends notifications. The settings page is `/settings/notifications` until the profile shell (M2-1) has a settings area.
20. **M1-6: what is audited.** Retrying a job and changing notification settings are audited (only the changed entries). Running jobs and reading notifications are not: the `job` table and `read_at` already record them.
21. **M1-6: smaller additions and gaps.** `flask mail test <address>` sends one mail right away to check the `MAIL_*` settings. The console backend logs at WARNING level, so mails that were not sent show up in production logs too. Quiet hours (§7.4) are not built yet.
22. **M1-10: all contact data needs `members.contact.view`.** Without it (Spefuxe, Füxe) the profile page shows no email, phone or address. With it, the email is always shown, the phone only with `show_phone` and the address only with `show_address`. Holders of `members.edit_any` and the member themselves see everything. The permission's description now says "E-Mail, Telefon, Adresse". The email shown is the contact email, else the login email.
23. **M1-10: former members are hidden.** `/members` lists only active members; holders of `members.edit_any` can add former members with the "Ehemalige" switch. For everyone else, the page `/m/<public_id>` of a former member is a 404.
24. **M1-10: no `profile.view_own` / `profile.edit_own` codes.** `/profile` only needs a login (`@require_login`), so every account can see its own data and change Biername, phone, address and the two visibility switches. Names and the contact email need `members.edit_any`. `/m/<public_id>` needs `members.directory.view`, also for one's own page.
25. **M1-10: one address, one person.** A contact email may not be another member's contact email (unique index) or another member's login email (checked by the service), so mails for members without a login cannot reach someone else.
26. **M1-10: the directory filters and sorts in Python.** SQLite's `LOWER()` and `LIKE` fold only ASCII letters, so "öz" would not find "Özil". Names are compared without case and accents (ä = a, as in DIN 5007-1), every search word must appear in the first name, last name or Biername, and the list is sorted by first name, like the member pickers on the org pages. There is no paging; the club is small.
27. **M1-10: changes to member data are audited with old and new values,** also phone and address. In the seed, everyone with `audit.view` (Senior, sysadmin) also holds `members.edit_any` and sees these values anyway.
28. **M1-12: an Austritt also ends the rank.** Besides Ämter, groups (§6.4) and direct roles, the open rank entry ends on the exit date. A Wiederaufnahme therefore starts without rank and rights ("Rang neu setzen") instead of silently restoring the old ones. A former member's page shows the last rank with its end date.
29. **M1-12: exits are recorded on the day or afterwards, never in advance.** The status changes to ENDED at once, so a future date would take rights away too early, and no job flips the status later. Periods that start after the exit date are deleted (66; before that, they ended on their first day).
30. **M1-12: the exit note is kept in the audit log only** (`members.exit`); `member` has no note column (§5.1). Ämter ended by an exit get the neutral end reason "Ausgeschieden", because every member can read the office history and the real reason (e.g. Ausschluss) is not theirs to see.
31. **M1-12: the Kassenwart notification has no link.** It names the member, the payment reference, the date and the reason. The Kassenwart usually lacks `members.edit_any` and could not open a former member's page. An exiting Kassenwart is not told about their own exit; if no other Kassenwart is in office, the person recording the exit gets a warning.
32. **M1-12: holders of `members.exit.record` also see former members** (directory switch and `/m/<public_id>`), so whoever records exits can undo them. In the seed, Senior and Schriftwart hold both codes. This extends 23.
33. **M1-12: logins and sessions.** Disabling a login raises `session_version`, and the user loader also rejects disabled accounts. Enabling changes nothing else (password, failed-login counter). The remember-me cookie carries `id:session_version` (`User.get_id`), so "Überall abmelden" ends it too; a test logs in from the remember cookie alone. Nobody disables their own login. The admin buttons are hidden on one's own member page; "Überall abmelden" for oneself is on `/profile`, and a POST to one's own `/m/<public_id>/logout-everywhere` logs out the same way.
34. **M1-12: `add_to_group` refuses former members,** as `assign_office` already did, and the "Rang ändern" button is hidden on a former member's page.
35. **M1-7: the invitation link is shown after a redirect, from the inviter's session.** "Neues Mitglied" and "Einladen" redirect to `/members/invited/<id>` (post/redirect/get), so reloading the page does not create a second member. The database holds only the token's SHA-256 hash, so the raw token of the newest link or QR invitation is kept in the inviter's (signed) session cookie, bound to their user id, and shown while that invitation is still open. Another inviter, or the same one after a newer invitation, sees only its state; a lost link means a new invitation. Emailed links are never shown to the inviter. Result and join pages send `Cache-Control: no-store` and `Referrer-Policy: no-referrer`.
36. **M1-7: one page for every unusable link.** Unknown, expired, revoked and used tokens, and members who got a login otherwise or left, all get the same 404 page "Link ungültig oder abgelaufen – bitte einen neuen anfordern". The roadmap's "Neuen Link anfordern" button that notifies the inviter (§3.3) is not built; the page tells the invitee to ask. Pending approval of new Spefuxe [Q7] is not built either.
37. **M1-7: delivery "none" and the starting rank.** "Neues Mitglied" can create the member without inviting them yet (the member page then offers "Einladen"). The rank starts on the entry date and is set through `change_rank` by the inviter, so it is audited as `org.rank.change`. Without `members.rank.change` only Spefux is offered and accepted (checked in the service, not only in the form). Nobody else is notified about the new member until they join.
38. **M1-7: emails on invitations.** An invitation's email is where the mail goes and the suggested login email; it may not belong to another member (contact or login email, as in 25). The invitee may choose a different login email on `/join`, but not another account's login email or another member's contact email. The mail is queued with `queue_mail('invite')` directly, not through `notify()`: it goes to the address on the invitation, and the invitee has no notification settings yet. The declared notification kind `invite` stays unused for now.
39. **M1-7: joining logs in and notifies.** A successful join creates the user, marks the invitation accepted (one conditional UPDATE, so a double submit cannot use it twice), logs the user in and sends `welcome` to the new member and `new_member` to the current Fuxmajor(s) (bell and mail per settings). The inviter is not notified separately. Someone already logged in is asked to log out first.
40. **M1-7: a new invitation revokes the member's older open ones,** so only the newest link works. An Austritt revokes open invitations too (listed in the `members.exit` audit entry), so an old link does not start working again after a Wiederaufnahme.
41. **M1-7: `/register` and `INVITE_CODE` are gone.** The K8/N1 regression test (`ADMIN_EMAIL` grants nothing) now joins through an invitation. QR codes are inline SVG from `segno` 1.6.6, in `core/platform/qr.py`; M4 adds the shared `qr_token` table there.
42. **M1-8: reset and email-change links are signed, not stored** (itsdangerous `URLSafeTimedSerializer` with `SECRET_KEY`, salts `password-reset` and `email-change`; no table). The reset token carries `uid`, `session_version` and a fingerprint of the password hash: the first 16 hex characters of its SHA-256, not the last 16 characters of the hash itself as planned, because the link travels by mail and ends up in logs. It still changes with every password change, also one made by `flask create-admin` without a session change. The reset raises `session_version` with a conditional UPDATE, so the link works once even for two simultaneous submits.
43. **M1-8: the email-change token also carries `from`,** a fingerprint of the login email at the time of the request. The link therefore works once and stops working when the login email changes otherwise. Confirming does not raise `session_version` (nobody is logged out): the link is often opened on another device, such as the phone, and the password was already checked when the change was requested.
44. **M1-8: confirming a new login email is a button (POST); the GET page changes nothing,** so mail scanners that open links cannot confirm. It works logged out, and logged in as someone else it changes only the link's account. "Taken" means another account's login email or another member's contact email (as in 25 and 38); it is checked on request and again on confirmation (409 page). The old address gets the mandatory `email_changed` mail, the new one the confirmation link (`email_change`); both are queued with `queue_mail`, which now takes a `dedupe_key`.
45. **M1-8: "Passwort vergessen?" never reveals whether an address has an account.** Every valid address gets the same page. Only enabled accounts get a mail, former members included, because their login stays usable (M1-12). Each account gets at most one mail per fixed 10-minute window (`dedupe_key` `password_reset:<user>:<window>`); confirmation links for a new login email are limited the same way per address. Every request is audited as `auth.password_reset.request` with the result `sent`, `throttled`, `unknown_email` (with the address, like failed logins) or `disabled`. Response times are not equalised: an unknown address is answered a few milliseconds faster. The login equalises its timing because it hashes a password; here the gain seemed too small for the effort.
46. **M1-8: the current password is checked like a login** when the password or the login email is changed. Wrong attempts count towards `MAX_FAILED_LOGINS`, lock the account for `LOGIN_LOCKOUT_MINUTES` (the login page too) and are audited as `auth.reauth_failed`, so a stolen session cannot be used to guess the password. A reset lifts the lock.
47. **M1-8: who stays logged in.** A reset ends every session, and the browser that used the link is logged out too, even if someone else was logged in there, and is sent to the login page. A password change ends all other sessions, and the current browser logs in again with the new `session_version`; it keeps "Angemeldet bleiben" if it had that cookie.
48. **M1-8: production refuses to start without `BASE_URL`** (it must start with `http://` or `https://`). Otherwise links in mails come from the request's `Host` header, and anyone could request a reset with a forged host and have the victim mailed a working link to the attacker's server. Servers must set `BASE_URL` before updating (README, step 4).
49. **M1-8: the routes belong to the auth module:** `/password/forgot`, `/password/reset/<token>`, `/settings/password`, `/settings/email` and `/settings/email/confirm/<token>`. `/profile` links to them under "Anmeldung", and the login page has "Passwort vergessen?". They need no permission codes (public or login). Pages whose URL contains a token send `Cache-Control: no-store` and `Referrer-Policy: no-referrer`, like `/join`, and an unusable link gets a 404 page that does not say why. The smoke test now also renders every public token route once with a valid token (fixture `valid_tokens`), so a new token route must add one.
50. **M1-9: the import preview lives in the page, not on the server.** The valid rows travel in a hidden field signed with itsdangerous (salt `member-import`, one hour), bound to the importing account's id; there is no table and no temporary file. The confirm step checks every row again. If anything changed meanwhile (an address now taken, a rank archived), nothing is imported and the preview is shown again (409) with the rows that are still valid, signed anew. All members, ranks and invitations are created in one transaction; a unique-index conflict from a parallel request rolls everything back.
51. **M1-9: what the file may contain.** At most 500 members per file (this also keeps the signed field well under Flask's 500 KB form limit), 20,000 rows including empty ones and 100 columns are read. CSV must be UTF-8 (with or without BOM); other encodings are refused with a hint ("CSV UTF-8" or .xlsx) instead of being guessed. The separator is whichever of `;` and `,` the header line uses more. Excel: only .xlsx (openpyxl 3.1.5), only the first sheet, formulas as their saved value, archives that unpack to more than 20 MB are refused. Row numbers in messages are the rows as Excel shows them (header = row 1).
52. **M1-9: duplicates.** An email that appears twice in the file is an error on *every* row with it, not only on the later ones, because the file does not say who owns the address (rule "one address, one person", see 25). An email that is already a member's contact or login email is an error. Same names (in the file or in the database) only warn: two people may share a name, but a list imported twice should stand out, since rows without email would otherwise be created again silently.
53. **M1-9: ranks and dates.** The rank is matched by key, label or abbreviation ("AH"), case-insensitive, among ranks in use. `members.import` alone may set every rank: the roadmap's bootstrap (§6.4) has the sysadmin import members with their initial ranks, and the sysadmin lacks `members.rank.change`. Ranks start on the entry date, else today, through `change_rank` (audited as `org.rank.change`, no notification, as the members have no login). An empty Eintritt leaves `joined_on` empty; an entry date in the future is refused, since the member would have no rank until then and it is usually a typo.
54. **M1-9: invitations from the import.** The option is shown only to importers who also hold `members.invite`, and the confirm step checks that permission again (a posted checkbox without it is ignored). Every created member with an email gets an email invitation through the M1-7 service; the mails are queued as jobs in the same transaction. Audit: one `members.create` per member (now with `source: import`), the rank changes and invitations as usual, and one `members.import` entry with the file name, the counts and the new member ids.
55. **M1-9: `MAX_CONTENT_LENGTH` is 2 MB for all requests,** fixed in `config.py`, not an environment variable. A larger request gets a flash message and a redirect to the same page if it can be opened with GET, otherwise to the start page (413 handler in `core/errors.py`). Nginx needs `client_max_body_size` above that (README), or its own 413 page appears first.
56. **M1-11: Tailwind v4.3.3, the newest v4 release, as standalone CLI.** `tools/build-css.sh` downloads it from GitHub into the git-ignored `tools/bin/` and checks it against SHA-256 hashes written into the script (from the release's `sha256sums.txt`), so a changed download stops the build. The built, minified `community/static/app.css` is committed; CI job `css` rebuilds it and fails when it differs. Tailwind v4 needs Safari 16.4+, Chrome 111+ or Firefox 128+; older browsers show the pages largely unstyled but usable **[verify the members' phones]**.
57. **M1-11: class names live only in templates.** `src/app.css` uses `source(none)` and `@source` for every `.html` under `community/`, so the build does not depend on what else is in the folder; no Python code builds classes. Shared styles are macros: `macros/ui.html` (`page_header`, `section_header`, `button`, `link_button`, `post_button`, `badge`, `alert`, `card`, `empty_state`, `stacked_list`, `table`, `empty_row`, plus class strings such as `link_class` and `cell`) and `macros/forms.html` (same API; `field()` passes extra attributes such as `rows=`, marks errors with `aria-invalid` and `aria-describedby`; `submit()` takes an optional variant). The actions of `page_header` go in a `{% call %}` block instead of an `actions` argument, because they are often forms or depend on permissions.
58. **M1-11: the menu is a plain list in `core/nav.py`** (`MAIN`, `ADMIN`; endpoint names only). A link is shown when the current user passes the access declaration of its route (the `@require_perm` code, or a login), so menu and route cannot disagree; the permissions are the same as the old `can()` checks in the layout (Mitglieder and Ämter: `members.directory.view`; Ränge and Jobs: `system.admin`). The "Verwaltung" group (Import, Gruppen, Semester, Ränge, Ressourcen, Protokoll, Jobs) appears when at least one of its links is allowed. "Ressourcen" (`bookings.manage_any`) is new in the menu; the link on the bookings page stays.
59. **M1-11: menus without JavaScript.** From 1024 px (Tailwind `lg`) the links sit in the top bar with "Verwaltung" as a `<details>` drop-down; below that one `<details>` "Menü" holds everything. The breakpoint is `lg`, not `md`, because the bar with "Verwaltung" does not fit 768 px. The bell with the unread count stays visible on phones; the current page is marked with `aria-current`. Drop-downs close when a page loads, not on a click elsewhere (that would need JavaScript). "Logout" is now "Abmelden".
60. **M1-11: htmx 1.9.12 is vendored** with its SHA-256 in `static/vendor/SHA256SUMS` (checked by CI and a test; it matches the SRI hash htmx publishes). `<meta name="htmx-config">` sets `selfRequestsOnly` (the CSRF header never goes to another site) and switches off htmx's inline indicator `<style>` (the rules are in `app.css`, so a later CSP needs no inline styles). `<body hx-headers>` carries the CSRF token on every page, so anonymous visitors now get a session cookie on every page, not only on pages with a form. No page uses htmx yet (first users: the `/me` widgets, M2-1).
61. **M1-11: static URLs carry a content hash** (`/static/app.css?v=<12 hex of its SHA-256>`, `core/assets.py`). Flask sends static files without `max-age`, so browsers could keep an old `app.css` for a while after a deploy and show new templates with old styles.
62. **M1-11: security headers for every response** (`core/security.py`): `X-Content-Type-Options: nosniff`, `Referrer-Policy: same-origin`, `X-Frame-Options: DENY`. They are set only where the view set none, so token pages keep `Referrer-Policy: no-referrer`. A Content-Security-Policy stays on the backlog; the copy button on the invitation page is an inline script that would then need a nonce or a static file.
63. **M1-11: look only, no behaviour.** Templates now share one style for lists, cards, tables, notices and buttons. Smaller visible changes: "Neu" buttons say what they create ("Neue Aufgabe", "Neue Ankündigung"); the "Neue Ressource" form sits below the list; the inputs for ending an Amt have labels; announcement texts keep their line breaks. Routes, form field names and flash categories are unchanged. The member page's "Verwaltung" section got `id="member-admin"`, and `test_member_lifecycle` now looks for that instead of the word, which the menu group also uses.

## 2026-10-11 — M0 implementation (Wegito/Community#1)

1. **One PR for M0, one commit per task.** The roadmap asks for one PR per task. M0 was delivered in the PR that added the roadmap. Each commit starts with its task ID, so the history still maps to the plan.
2. **M0-13 (package layout) ran before M0-5 … M0-12.** The roadmap puts it last. Running it first meant each fix was written once, in its final place. The M0-4 fix was still made on the old layout first, so that commit shows the original bug clearly.
3. **Dependencies were upgraded, not only completed (M0-3).** pip-audit reported known vulnerabilities in the old pins (Jinja2 3.1.4, Werkzeug 3.0.x). SQLAlchemy stays on the 2.0 line because Flask-SQLAlchemy 3.1 compatibility with 2.1 was not checked.
4. **Chores (M0-10): the assignee toggles "done" instead of editing.** The roadmap says "only the assignee or an admin edits". Admins edit everything; the assignee gets an "Erledigt / Wieder öffnen" button. This stops assignees from reassigning or renaming their own chores before real permissions arrive in M1-3 and M2-3.
5. **`X-Forwarded-Host` is never trusted (M0-5).** `TRUSTED_PROXY_HOPS` applies to `X-Forwarded-For` and `X-Forwarded-Proto` only; Nginx passes the host in the `Host` header. Trusting a client-controlled host header would let attackers poison links in future emails (password reset, invites).
6. **The unused htmx script was removed (M0-12).** M1-11 brings it back as a local, pinned file.
7. **A form macro (`templates/macros/forms.html`) was added in M0-9.** The roadmap plans macros in M1-11, but the new 10-character password rule needs visible error messages now.
8. **Bookings are serialised with a no-op `UPDATE` on the resource row (M0-11)** before the overlap check. On SQLite this takes the write lock; on Postgres it locks the row. `tests/test_bookings.py` proves the lock is held during the check.

## 2026-10-11 — Pre-push review of M0

An independent review (four reviewers, each finding checked by a second agent trying to refute it) confirmed 14 distinct issues; all are fixed in the commits marked "fix" in Wegito/Community#1. The ones that change design:

9. **SQLite migrations run with foreign keys off** (`migrations/env.py`), followed by `PRAGMA foreign_key_check`. Batch table rebuilds cannot drop a referenced table while foreign keys are enforced.
10. **Login attempts are counted before the password check, in one atomic UPDATE** (`User.reserve_login_attempt`). The attempt that reaches the limit sets the lock and is still checked. A locked account does the same hashing work as a wrong password.
11. **`.env` is loaded by the entry points, not by `community/config.py`.** `wsgi.py` loads it; the `flask` command loads it by itself. Tests no longer depend on a developer's `.env`.
12. **Test-client requests run in their own app context** (`tests/conftest.py`), so login state comes from the session cookie and the user loader, as in production.
13. **`parse_cents` rejects more than two decimal places** instead of rounding, because `1.234` is ambiguous between German and English notation.
